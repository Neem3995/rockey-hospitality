## Changes and concurrency reasoning

- [UserRepository](../src/main/java/com/rockey/hospitality/repository/UserRepository.java), lines 19–22: separate `findForLogin`, with bound JPQL `u.email = :email` and `PESSIMISTIC_WRITE`. Registration/team writes and login input normalize email; the equality predicate can use the existing unique email key rather than wrapping the indexed column in a case function. The ordinary `findByEmailIgnoreCase` at line 18 remains unlocked for identity loading.
- [AuthService](../src/main/java/com/rockey/hospitality/service/AuthService.java), `login` lines 47–58: acquire the account lock before active/password validation and hold it through `startSession` (line 96) and transaction commit. `logout` lines 82–86 uses existing `findForUpdate` before clearing refresh state. Refresh retains its existing locked hash lookup.
- [AuthServiceTest](../src/test/java/com/rockey/hospitality/service/AuthServiceTest.java): changed login/logout repository stubs and verified that these paths do not use the ordinary email/id lookups.
- [HousekeepingMySqlTest](../src/test/java/com/rockey/hospitality/hardening/HousekeepingMySqlTest.java), lines 190–384: added both transaction orders for login/deactivation, identity changes, refresh and logout. Real Spring transaction management, repositories and database persistence are used. Only BCrypt matching is spied to pause a login after its real lookup. Latches coordinate the gates; database metadata must show the competing connection waiting before release. Assertions check account state, revoked/superseded cookies and the last session's persisted hash.

Before the correction, an unlocked login could load active/role/email values, an ADMIN could commit changes, and a later refresh-field mutation could flush the earlier account values with Hibernate's default static update mapping. User has neither `@Version` nor `@DynamicUpdate`. This is a source-supported stale-write risk; actual SQL and an exploit were not reproduced in this pass.

With the correction, a login first obtains the user lock, so an administrative edit waits and subsequently applies its values/revocation. If the edit commits first, the locking login read sees current account state and rejects a disabled account or the old email. Logout and refresh likewise serialize user session writes; the last successful writer governs the single refresh session. Generic credential failures, limiter calls, DTO/status/cookie contracts and refresh revocation remain intact. Logout still does not blacklist issued access JWTs; other existing JWT/account validation continues to apply.

Login/logout/refresh acquire one account write lock and introduce no Room/Task lock or inverse lock order. Existing assignment writes use User -> Room -> Task ordering; account edits lock their target before eligibility checks. BCrypt now runs while the account is locked, intentionally serializing login/session/account writes for that identity. Actual lock plans, collation behavior, contention and deadlocks are not certified without live execution. The predicate relies on the application's normalized stored-email invariant; manually provisioned mixed-case data on a case-sensitive database needs validation before use.

The new tests retain the existing two safety gates: exact loopback disposable JDBC URL and `SELECT DATABASE() = rockey_hospitality_hardening` before fixture deletion. Their additional metadata reads require access to `performance_schema.data_lock_waits` and `performance_schema.threads`. No database permission was changed. These tests are retained as **NOT RUN**, not passed regressions.
